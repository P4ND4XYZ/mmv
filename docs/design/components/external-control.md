# CLI・単一起動・外部操作

[設計全体像に戻る](../index.md)

## 責務と対象範囲

`mmv`をファイル表示と外部操作の共通入口にし、既存の1ウィンドウへ要求を配送します。CLIは処理結果を返して終了し、GUIはウィンドウを閉じるまで動作します。通信と起動制御は`infra`、文書操作の判断は`app`、描画と移動は`ui`が担当します。

## 起動とプロセスの役割

CLIとGUIの役割を分けます。同じ実行ファイルを内部的なGUI起動モードで実行できる構成とし、利用者向けに別のGUIコマンドや操作対象インスタンスの選択は追加しません。引数の解析・ヘルプ・使い方エラーの処理はGUIの初期化より前に行います。

| 状況 | CLIとGUIの処理 |
|---|---|
| GUIへ接続できる | 既存GUIへ要求を送信し、その要求の応答を待つ |
| 未起動でファイルを開く | GUIプロセスを起動し、接続可能になってから要求を渡し、読み込み結果まで待つ |
| 未起動でスクロール・履歴移動 | GUIを起動せず失敗を返す |
| 起動済みだが接続できない | 接続失敗として返す。別のGUIを起動しない |

単一起動にはWindowsの名前付き同期オブジェクトを使います。GUIの生存を示す所有権と起動中の調停を行い、同時に複数の`open`が来てもGUIを複数起動しないようにします。起動する権利を得た後にも生存状態を再確認し、他のCLIが起動したGUIへ接続できるようにします。

生存ロックはGUIが保持し、終了・異常終了で解放されるものを使います。Pipeへの接続失敗だけから未起動と判断しません。Named Pipeと同期オブジェクトの接続・操作権限は現在の利用者に限定します。

## 要求・応答の契約

### 要求

- プロトコルの版、要求ID、操作、必要な引数を持たせる。
- ファイルパスはCLI側でカレントディレクトリを基準に絶対パスへ解決して送る。GUI側のカレントディレクトリを使わない。
- 操作は公開CLIと同じ種類に限定し、シェルコマンドや任意の実行内容を渡す仕組みにはしない。
- Pipeの読み書きはUIスレッド外で実行し、受信済みの操作をGUIの処理へ配送する。Pipeから直接`app`やGPUIの状態を変更しない。

### 応答

- 要求ID、成功・失敗、失敗理由を対応付ける。文書の世代番号をCLI要求IDとして流用しない。
- ファイルを開く操作は、対応するファイル読み込みが成功・失敗した時点で応答する。送信完了やGUI起動完了を、ファイル表示の成功として返さない。
- Mermaid生成、画像取得、本文の最終描画完了までは待たない。
- スクロール・先頭末尾移動・履歴移動も、その操作の処理結果を返す。履歴移動でファイル読み込みが必要なら、その成否を待つ。
- 古い読み込み結果を表示へ適用しない場合も、対応する要求元への読み込み結果の応答は完了させる。GUIの最新要求だけに応答し、他のCLIを待たせ続ける実装にはしない。

CLIへの成功応答は、後続の別要求による表示変更まで禁止するものではありません。複数要求の応答先と、現在画面へ適用できる文書世代を独立して扱います。

応答は公開仕様の終了コードと標準出力・標準エラーへ変換します。通常の成功時は何も出力しません。通信途中の切断、不正な応答、GUIの終了を成功扱いにしません。

## 待機と再送

既存GUIへの接続は5秒、GUI起動は30秒、ファイル読み込み結果は30秒を上限とします。各段階の開始時点から期限を管理し、内部の接続再試行によって同じ段階の期限を延長しません。通信の読み書きと、読み込みを伴わない操作の応答待ちも無期限にしない構成にします。

タイムアウトではCLIの待機と接続だけを終了します。GUIを強制終了せず、送信済みの操作も取り消しません。要求を自動再送しないため、応答を失った操作を重複実行しません。

CLI切断後に読み込みが完了した場合も、有効な文書操作であればGUI側の処理は継続します。応答先を解放し、接続単位のタスクや待機を残さないようにします。

## フォーカスと入力モード

- GUIの初回ウィンドウ生成を含め、外部アプリのフォーカスを奪わない。プロトタイプの無条件な`activate`呼び出しは製品の起動経路に残さない。
- 既存GUIへ要求を送った際も、前面化・アクティブ化や本文へのフォーカス移動を行わない。
- Search・Commandでも操作を配送し、モードと入力文字列を維持する。共通移動処理にはキーボードのNormal専用ガードを持ち込まない。
- 文書更新後の検索と位置の扱いは[文書操作と閲覧状態](document-operations.md)に従う。コマンド入力をCLI操作として実行したり、検索確定に変換したりしない。

非アクティブ起動は、ウィンドウ生成オプションの設定だけで満たしたと判断せず、Windows上で外部アプリのフォーカスを取得して確認します。

## 先行検証と設計判断

CLIの終了とGUIの生存を分ける必要があるため、GUIをCLIと同じプロセスでそのまま動かし続ける構成にはしません。GUI起動用の内部引数、Pipeのメッセージ形式と境界、同期オブジェクトとアクセス制御を、実装時に一体で具体化します。公開コマンド・待機上限・成功の意味は変更しません。

第1段階では、GUIが起動して非アクティブなまま接続を受け付けること、要求ID付きの応答をCLIが受け取って終了できること、同時起動が1ウィンドウに収束することを小さく検証します。正式コマンドと全操作の接続は、文書操作と履歴を整えた後に行います。

## 検証観点

- [ ] CLI引数の単体テストで、省略形、サブコマンドと同名のファイル、空白・日本語のパス、終了コードを確認する。
- [ ] 異なるカレントディレクトリから既存GUIへ接続し、CLI側を基準にファイルを開けることを確認する。
- [ ] 同時起動、起動途中、接続不能、GUIの異常終了を含むプロセス結合テストで単一起動を確認する。
- [ ] 読み込み失敗、逆順完了、応答途中の切断、タイムアウトで要求IDと結果が混ざらず、自動再送しないことを確認する。
- [ ] GPUI結合テストでSearch・Command中のファイル切り替え、スクロール、履歴移動が入力を維持することを確認する。
- [ ] Windows実機で初回起動と既存GUI操作の両方について、呼び出し元のフォーカスが維持されることを確認する。
