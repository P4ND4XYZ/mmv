# CLI・単一起動・外部操作

[設計全体像に戻る](../index.md)

## 責務と対象範囲

`mmv`をファイル表示と外部操作の共通入口にし、既存の1ウィンドウへ要求を配送します。CLIは処理結果を返して終了し、GUIはウィンドウを閉じるまで動作します。通信と起動制御は`infra`、文書操作の判断は`app`、描画と移動は`ui`が担当します。

## 起動とプロセスの役割

CLIとGUIの役割を分けます。同じ実行ファイルを内部的なGUI起動モードで実行できる構成とし、利用者向けに別のGUIコマンドや操作対象インスタンスの選択は追加しません。引数の解析・ヘルプ・使い方エラーの処理はGUIの初期化より前に行います。

| 状況 | CLIとGUIの処理 |
|---|---|
| GUIへ接続できる | 既存GUIへ要求を送信し、その要求の応答を待つ |
| 未起動でファイルを開く | GUIプロセスを起動し、接続可能になってから要求を渡し、読み込み結果まで待つ |
| 未起動でスクロール・履歴移動 | GUIを起動せず失敗を返す |
| 起動済みだが接続できない | 接続失敗として返す。別のGUIを起動しない |

単一起動にはWindowsの名前付き同期オブジェクトを使います。GUIの生存を示す所有権と起動中の調停を行い、同時に複数の`open`が来てもGUIを複数起動しないようにします。起動する権利を得た後にも生存状態を再確認し、他のCLIが起動したGUIへ接続できるようにします。

生存ロックはGUIが保持し、終了・異常終了で解放されるものを使います。Pipeへの接続失敗だけから未起動と判断しません。Named Pipeと同期オブジェクトの接続・操作権限は現在の利用者に限定します。

## 非同期処理とスレッド境界

Windowsの直接依存には既存lockfileと同じTokioを使い、`rt`・`net`・`io-util`・`sync`・`time`・`macros`だけを有効にします。`full`やmulti-thread runtimeは使いません。

| 実行場所 | 責務と寿命 |
|---|---|
| CLIのmainスレッド | 引数処理後に`current_thread` runtimeを作り、1回の起動調停と要求送受信を`block_on`する |
| GUIのmainスレッド | GPUIと生存Mutexを保持し、文書操作と応答先の登録・解放だけを行う |
| 専用IPCスレッド | `current_thread` runtimeで接続受付と接続ごとの非同期タスクを実行する |
| GPUI background executor | 受信・切断通知のイベント待機を行い、終了時にはIPCスレッドのjoinを行う |

MutexはWindowsのスレッド所有であり、async task所有ではありません。`InstanceGuard`は取得したスレッドで解放し、`spawn`や`spawn_blocking`へ移しません。同じスレッドで複数の起動調停を並行実行しません。GUIの生存MutexはウィンドウとIPCの終了確認後まで保持します。

IPC接続タスクは`JoinSet`で管理し、上限128とします。GUI宛て受信キューも独立に128件までです。上限到達時は新規接続または新規要求を拒否して接続を閉じ、空き待ちのタスクや無制限キューを作りません。キューへの投入は`try_send`で行います。完了タスクは受付中にも回収します。

### GUI配送と切断通知の順序

受信は非同期`recv`、切断は`Notify`で待機し、10msのポーリングは行いません。TokioからのクロススレッドwakeはGPUIのSendなbackground taskで受け、foreground taskはその結果を受けてViewerを更新します。イベント待機は常に1個だけです。1イベントごとにUI executorへ実行権を返し、連続入力でUIを占有しません。

外部要求IDとは別に、接続ごとに内部`ConnectionId`と生存状態を持たせます。応答先は文書読み込みIDに対応付け、同じ外部要求IDを持つ複数の接続も混同しません。切断・期限切れ・終了時には接続タスクが生存状態をfalseに公開してから`Notify`を通知します。通知は1個のpermitへ集約されるため、受信キュー満杯でも失われず、切断通知のバックログも増えません。GUIは通知と各配送時に応答先の生存状態を確認します。

配送より先に切断した要求も、キューに受理済みなら文書操作は実行しますが、死んだ応答先は登録しません。登録直後に切断した場合も保存された通知で解放されます。読み込みが永久に完了しない場合にも、切断したCLIの応答先を保持し続けません。切断通知は文書操作の取消通知ではありません。

## 要求・応答の契約

### 要求

- プロトコルの版、要求ID、操作、必要な引数を持たせる。
- ファイルパスはCLI側でカレントディレクトリを基準に絶対パスへ解決して送る。GUI側のカレントディレクトリを使わない。
- 操作は公開CLIと同じ種類に限定し、シェルコマンドや任意の実行内容を渡す仕組みにはしない。
- Pipeの読み書きはUIスレッド外で実行し、受信済みの操作をGUIの処理へ配送する。Pipeから直接`app`やGPUIの状態を変更しない。

### 応答

- 要求ID、成功・失敗、失敗理由を対応付ける。文書の世代番号をCLI要求IDとして流用しない。
- ファイルを開く操作は、対応するファイル読み込みが成功・失敗した時点で応答する。送信完了やGUI起動完了を、ファイル表示の成功として返さない。
- Mermaid生成、画像取得、本文の最終描画完了までは待たない。
- スクロール・先頭末尾移動・履歴移動も、その操作の処理結果を返す。履歴移動でファイル読み込みが必要なら、その成否を待つ。
- 古い読み込み結果を表示へ適用しない場合も、対応する要求元への読み込み結果の応答は完了させる。GUIの最新要求だけに応答し、他のCLIを待たせ続ける実装にはしない。

CLIへの成功応答は、後続の別要求による表示変更まで禁止するものではありません。複数要求の応答先と、現在画面へ適用できる文書世代を独立して扱います。

応答は公開仕様の終了コードと標準出力・標準エラーへ変換します。通常の成功時は何も出力しません。通信途中の切断、不正な応答、GUIの終了を成功扱いにしません。

## 待機と再送

既存GUIへの接続は5秒、GUI起動は30秒、ファイル読み込み結果は30秒を上限とします。各段階の開始時点から期限を管理し、内部の接続再試行によって同じ段階の期限を延長しません。通信の読み書きと、読み込みを伴わない操作の応答待ちも無期限にしない構成にします。

タイムアウトではCLIの待機と接続だけを終了します。GUIを強制終了せず、送信済みの操作も取り消しません。要求を自動再送しないため、応答を失った操作を重複実行しません。

CLI切断後に読み込みが完了した場合も、有効な文書操作であればGUI側の処理は継続します。応答先を解放し、接続単位のタスクや待機を残さないようにします。

要求のdecode直後、キュー投入前に、Tokioの受信済みバッファとカーネルPipeの状態を1回だけ非待機で検査します。すでに余分なデータや切断が見える要求は投入前に拒否します。検査は`try_read`と`PeekNamedPipe`で行い、独自OVERLAPPED待ちやポーリングは追加しません。検査後の変化は従来同様に受付と競合し得るため、受理済み操作は取り消しません。

応答待ちはoneshotだけで待たず、Pipeのread readinessと1バイトの読み取りも同時に待ちます。切断・余分なデータ・応答期限のいずれでも接続タスクを終了します。部分フレームの読み書きを取り消した接続は再利用せず、送信済みの操作を再送しません。応答後の既存の1バイトreceiptは維持し、サーバーはreceiptを受けるまで接続を保持します。CLIもreceipt後のサーバー切断を同じ応答期限内で確認してから接続を破棄します。

### セキュリティとI/O資源

PipeとMutexはWin32で現在ユーザーだけの保護DACL・明示owner・非継承handleを作成し、既存オブジェクトへの接続でもownerとACLを検証します。クライアントは`READ_CONTROL`と`SECURITY_SQOS_PRESENT | SECURITY_IDENTIFICATION`を維持します。同一ユーザーのプロセスは信頼境界の内側であり、アプリケーション固有の認証ではありません。

検証したOVERLAPPED対応handleの唯一の所有権を、runtime内でTokioへ引き渡します。登録失敗時もTokio側が閉じるため、二重解放しません。読み書き・接続・バッファ・OVERLAPPEDと完了通知はTokio/Mioが管理し、独自イベントやWin32 completion waitは持ちません。

Tokio/Mioは書き込みを内部バッファへ受け付けた時点で完了を返し、通常のDropでは保留書き込みを残すことがあります。このため接続破棄時だけ`CancelIoEx(handle, NULL)`で当該handleの保留I/Oを取り消します。バッファとOVERLAPPEDはMioが完了まで所有し、呼び出し元の借用バッファを残しません。`FlushFileBuffers`や手動の完了待ちは使わず、読み取らないクライアントにも終了を妨げさせません。

### 初期化と終了

`PipeServer::bind`は専用スレッドのruntimeと最初のsecure listenerが準備できてから成功を返します。スレッド・runtime・ACL・Pipe作成の初期化失敗は呼び出し元へ返します。ウィンドウ生成に失敗した場合も受付停止を要求し、GPUI background executorのjoin完了をapp quitで待機します。

終了は「受付停止 → 接続futureの取消とJoinSetの回収 → runtime終了 → IPCスレッドjoin」の順です。UIは停止要求だけを同期的に出し、joinはbackground executorへ移します。ウィンドウ解放後にapp quitが来ても同じjoin taskを待機し、二重停止・二重joinを起こしません。

## フォーカスと入力モード

- GUIの初回ウィンドウ生成を含め、外部アプリのフォーカスを奪わない。プロトタイプの無条件な`activate`呼び出しは製品の起動経路に残さない。
- 既存GUIへ要求を送った際も、前面化・アクティブ化や本文へのフォーカス移動を行わない。
- Search・Commandでも操作を配送し、モードと入力文字列を維持する。共通移動処理にはキーボードのNormal専用ガードを持ち込まない。
- 文書更新後の検索と位置の扱いは[文書操作と閲覧状態](document-operations.md)に従う。コマンド入力をCLI操作として実行したり、検索確定に変換したりしない。

非アクティブ起動は、ウィンドウ生成オプションの設定だけで満たしたと判断せず、Windows上で外部アプリのフォーカスを取得して確認します。

## 先行検証と設計判断

CLIの終了とGUIの生存を分ける必要があるため、GUIをCLIと同じプロセスでそのまま動かし続ける構成にはしません。GUI起動用の内部引数、Pipeのメッセージ形式と境界、同期オブジェクトとアクセス制御を、実装時に一体で具体化します。公開コマンド・待機上限・成功の意味は変更しません。

第1段階では、GUIが起動して非アクティブなまま接続を受け付けること、要求ID付きの応答をCLIが受け取って終了できること、同時起動が1ウィンドウに収束することを小さく検証します。正式コマンドと全操作の接続は、文書操作と履歴を整えた後に行います。

## 検証観点

- [ ] CLI引数の単体テストで、省略形、サブコマンドと同名のファイル、空白・日本語のパス、終了コードを確認する。
- [ ] 異なるカレントディレクトリから既存GUIへ接続し、CLI側を基準にファイルを開けることを確認する。
- [ ] 同時起動、起動途中、接続不能、GUIの異常終了を含むプロセス結合テストで単一起動を確認する。
- [ ] 読み込み失敗、逆順完了、応答途中の切断、タイムアウトで要求IDと結果が混ざらず、自動再送しないことを確認する。
- [ ] GPUI結合テストでSearch・Command中のファイル切り替え、スクロール、履歴移動が入力を維持することを確認する。
- [ ] Windows実機で初回起動と既存GUI操作の両方について、呼び出し元のフォーカスが維持されることを確認する。
