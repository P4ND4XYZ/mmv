## 対応する要件と設計の範囲

表示専用・全ファイル表示・Luaによる初期表示設定・左右フォーカス移動・文書に応じたルート追従・フォルダー展開時の表示・アクセスエラー・リンク先非展開の振る舞いと受け入れ条件は、[ファイルツリーの要件](../../requirements/features/file-tree.md)を正本とします。ツリーからのファイルオープンは将来対応です。

2段階入力は既存の`g g`と同じGPUI機構を使い、フォルダー展開時の一覧取得は非同期で行う方針です。こうした実装方法は本書で扱います。以下のAPI名・既定値や未決定の操作案を、要件として確定済みとは扱いません。

### Lua設定の推奨案（API未決定）

既存の`%LOCALAPPDATA%\mmv\init.lua`内の`mmv.setup`に、次のようなboolean設定を加える案です。

```lua
require("mmv").setup({
  tree = {
    visible = true,
  },
})
```

`tree.visible`は起動時の値とし、省略時は`false`を推奨します。既存の本文中心の画面を標準に保てます。起動後のキー操作で変更した可視状態はセッション中だけ保持し、Luaファイルへ書き戻しません。別文書・別プロジェクトへ移動しても可視状態は保持し、再起動時にLuaの値へ戻します。表示ありで起動しても初期フォーカスは本文とする案です。

既存の表示設定仕様に合わせ、文書側のLuaは実行せず、CLI操作・F5で設定を再読み込みしません。boolean以外は設定エラーとし、設定全体を標準値へ戻す既存方針に含める案です。初期表示設定の実装は、未導入のLua設定基盤との接続が必要です。キーマップ設定APIの追加までは含みません。

## ルート検出の推奨案

`.marksman.toml`は候補として適切です。[Marksman公式のプロジェクト説明](https://github.com/artempyanykh/marksman/blob/main/docs/features.md#workspace-folders-project-roots-and-single-file-mode)はVCSルートや同ファイルをプロジェクトの印として挙げ、実際の検出はエディターによって異なるとしています。[公式README](https://github.com/artempyanykh/marksman#faq)は空ファイルの作成も案内しています（2026-11-09確認）。以下の優先順位は**mmv向けの提案**であり、Marksman共通のアルゴリズムだという主張ではありません。

1. 読み込みに成功して採用された文書の親から、祖先を1段ずつ調べる。cwdや起動時の文書を固定基準にしない。
2. 各階層で`.marksman.toml`という通常ファイル、または`.git`というディレクトリ／通常ファイルがあれば、その階層で探索を止める。`.git`のファイル形態も候補に含める。
3. 同じ階層に両方ある場合は同じルートになる。表示する検出理由は`.marksman.toml`を優先する案とする。
4. どちらもなければ**文書の直接の親ディレクトリ**を使う。ドライブ／共有のルートまで探索しても、そこを無条件にツリールートにはしない。

距離をマーカー種別より優先します。たとえば`repo/.git`と`repo/docs/.marksman.toml`があれば、`docs/a.md`は`docs`を使います。逆に`notes/.marksman.toml`内の`notes/sub/.git`にある文書は`sub`を使います。外側のMarksmanマーカーを必ず優先する方式ではありません。

| 方式 | 利点 | トレードオフ・判断 |
|---|---|---|
| 最も近い`.marksman.toml`または`.git`（推奨） | 明示的な文書集合とGit利用の両方に対応し、入れ子の近い境界を尊重 | 子Gitリポジトリに入ると外側のノート集合から切り替わる |
| 全祖先の`.marksman.toml`を先に探し、なければ`.git` | Markdown集合を強く優先できる | 遠いマーカーが近いリポジトリ境界を越える |
| `.marksman.toml`だけ | 文書集合の意図が明確 | マーカーを置かないGit利用者には親ディレクトリしか見えない |
| 専用マーカー／ユーザーによるルート指定 | mmv独自の意味や例外を表せる | 新規設定と操作の仕様が増えるため、必要性が出るまで保留 |

マーカーは存在だけを見る案とし、TOML設定の読み込み・LSP起動・Gitコマンド実行は行いません。空・不正TOMLでも印として扱い、mmvからマーカーを生成・変更しません。これなら読み取り専用と整合しますが、Marksmanの除外設定などを引き継ぐものではないことを明確にします。

ルートは表示範囲であり、ファイルアクセスの許可境界ではありません。既存のCLI・文書内リンクでルート外に移動できる契約は維持する案です。

### パスと切り替えの論点

- 推奨：現在文書の`DocumentKey`が表す正規化済みパスの親を使う。既存の同一性確認に合わせられるが、symlink経由で開いた場合は見かけの配置と異なる。表示名に元パスを使うかも要決定。
- 合意済み：別プロジェクト文書の採用成功後にルートを追従させる。失敗・古い完了では現在のルートや現在文書の強調を変えない。同じルートなら展開状態を保持し、異なるルートなら初期化する詳細は推奨案。
- ルートを毎回追従させると入れ子で表示範囲が変わる。ルート固定／複数ルートは別案として保留する。
- マーカーの権限エラーを「存在しない」と同一視しない。推奨は探索を打ち切って文書の親を暫定表示し、検出失敗をツリー内に示す。本文表示は継続する。
- ドライブとUNC共有の最上位で終了し、ネットワーク・大量階層でもUIを待たせない。再評価中に別文書へ移った場合は古い結果を捨てる。

合意済みの範囲を前提に、以下の詳細を整理します。フォーカス移動キーは合意済みですが、表示切替キー・寸法・永続化などは未決定です。

## キーとフォーカスの合意方針・検証事項

| 操作 | 方針と決定状態 |
|---|---|
| 本文から左のツリーへ | **採用：`Ctrl+W`を押した後に`h`**（登録表記候補`"ctrl-w h"`） |
| ツリーから右の本文へ | **採用：`Ctrl+W`を押した後に`l`**（登録表記候補`"ctrl-w l"`） |
| 既に移動先にいる／ツリー非表示 | 何もしない案。フォーカス操作だけでツリーを自動表示しない |
| ツリーの表示切り替え | `Ctrl+Shift+e`を推奨（未決定）。表示するだけなら本文フォーカスを維持。ツリーにフォーカスがある状態で隠した場合は本文へ戻す |
| 本文へ戻る補助操作 | 待機中でないツリー内の`Esc`で本文へ戻す案。ツリー自体は隠さない |
| 行選択 | ツリー内の`↑`／`↓`。`j`／`k`も同じ操作に割り当てる候補。本文スクロールは同時実行しない |
| 階層操作 | `→`は展開／展開済みなら先頭の子へ、`←`は折り畳み／閉じていれば親へ。ルートの親へは移動しない。Enterはフォルダー開閉のみで、ファイル行では何もしない |

### 既存機構を使う根拠

- [キー登録](../../../src/ui/input.rs)の`bind_keys`には`KeyBinding::new("g g", FirstLine, Some("EvaluationNormal"))`がある。[ナビゲーション仕様](../../requirements/features/navigation.md)にも`gg`があり、[モードの結合テスト](../../../src/ui/tests/modes.rs)では`g`を2回送信して先頭位置を確認する。2段階入力は既存機構で扱えており、独自の連続入力処理を新設する前提を置かない。
- 現行mmvの登録に`Ctrl+W`との競合はない。`Ctrl+b`／`Ctrl+f`はページ移動、`Ctrl+o`／`Ctrl+i`は履歴、`F5`は本文再読み込みを維持する。`f`は未実装でもリンクパネルの仕様上予約済みとして扱う。
- 方向を指定するVim風操作を採用し、以前の`F6`往復案は採用しない。表示切り替えとフォーカス移動は別の操作とする。
- mmvの登録確認と既存テストの読解は、GPUI標準バインド・OS・常駐ソフトを含む実行時の競合検証ではない。Ctrlを離した`h/l`を基本とし、押したままの`Ctrl+h/l`も別名として許容するかは未決定。

Normalかつ共通選択パネルが閉じているときだけ受け付ける案です。Search・Command・リンクパネル・IME変換中は入力を奪いません。ツリーのクリック操作も同じ制約とする案です。外部CLIは従来どおり入力中も受け付けます。

[本文の描画](../../../src/ui/document.rs)では`EvaluationNormal`を本文に付けているため、登録を追加するだけではツリー側からの移動を完成できません。左右移動用アクション、ツリーのフォーカス、両領域で利用できる適切なコンテキストが必要です。本文用のスクロール等をツリーから同時実行させず、再描画や外部CLIだけでフォーカスを奪わないようにします。

## 利用状況ごとの合意方針と詳細案

### 別プロジェクトへ移動する

例：`C:\work\alpha\docs\a.md`を表示中に、エディターがCLIで`C:\work\beta\README.md`を開く。両方のプロジェクトに`.git`がある場合、合意方針に従いbeta文書の採用成功後にbetaルートへ切り替えます。読み込み失敗ならalpha本文とalphaツリーを維持します。リンク・戻る／進むによる移動でも同じ規則を使います。

同じルートなら展開状態を保持し、別ルートなら古い選択・展開を破棄して現在文書までの祖先を展開する案を推奨します。可視状態と本文／ツリーのフォーカス先は保持します。別ルートの検出中は旧一覧を新しい文書のツリーとして見せず「ルート確認中」とし、操作できない状態にします。A→B→Aでも古いAの結果を再利用しないよう要求世代で区別します。非表示中は現在文書の変更だけ記録し、次の表示時に検出・列挙します。

この方式は現在読んでいる文書との対応が明快ですが、入れ子の`.marksman.toml`／`.git`でもルートが変わり、以前の展開状態は戻りません。プロジェクト別キャッシュやルート固定は便利になる一方、状態管理が増えるため初期案では保留します。

### 大規模フォルダーを開く

例：`node_modules`や画像10万件のフォルダーを含むリポジトリ。全ファイル表示を実現するために全階層を起動時に走査すると、不要なI/Oとメモリ消費が生じます。合意方針は展開時に直下だけを非同期取得する遅延列挙です。ファイル内容・サムネイルは読み込みません。`node_modules`を勝手に除外する代わりに、未展開なら内部を読まない方式にします。

単一フォルダー自体が巨大な場合は、取得を小分けにし、画面内の行だけ描画する方式を検討します。件数／処理時間の上限に達したら「一部表示・続きを取得」と表示し、空や取得完了と誤認させません。上限値はWindowsと共有フォルダーで計測して決めます。部分取得で全体の名前順は保証できないため、「取得済み範囲内のフォルダー優先・名前順」とし、選択は行番号でなく項目IDで維持する案です。厳密な全体ソートを要求するなら列挙完了までの待ち時間・メモリとの比較が必要です。

### アクセスを拒否される

例：共有フォルダー内の`public`と`restricted`のうち、`restricted`だけ一覧権限がない。合意方針に従い、拒否された枝だけ「アクセスできません」と表示し、他の枝と本文は利用可能なままにします。アクセス拒否を空フォルダー扱いにせず、ツリー内の再試行操作を用意します。自動再試行を繰り返したり、昇格を求めたりしません。

祖先マーカーの検出自体で拒否された場合は「マーカーなし」と断定せず、文書の親を暫定ルートにして理由を表示します。その親も列挙できなければツリー全体にエラーと再試行を表示し、本文は保持します。既存一覧の更新に失敗した場合は、以前の行を残すなら「更新失敗・古い一覧」と明示します。Search／Commandの入力行をツリーエラーで置き換えない案です。

### シンボリックリンク／junctionがある

例：`repo\assets`が別ドライブの巨大な素材集を指す、または`repo\loop`が親を指すjunctionになっている。合意方針は項目をリンクとして表示し、初期版では手動展開を含めてリンク先を列挙しない方式です。ファイルリンクも表示だけにし、壊れたリンクでも名前を残してリンク先を利用できない状態を区別します。これはファイル種別のフィルターではなく、再帰探索の境界です。

この制限で循環や意図しない外部共有への大量アクセスを避けられますが、リンク先の構造は見られません。将来追従させるなら、ルート外を許すか、訪問済みディレクトリの同一性、深さ制限を別途設計します。Windowsのすべてのreparse pointを単純にsymlink扱いせず、junctionやクラウドプレースホルダー等の分類を実機で確認する必要があります。

なお、CLIでsymlink経由のMarkdownを開いた場合の本文読み込みは既存動作のままです。ルートは正規化済み`DocumentKey`の親を使う推奨案なので、リンク元ではなく実体側のプロジェクトになります。ツリー内のリンク非追従と、この文書ルートの決め方は別の判断として明示します。

## 採用する場合の実装境界

- `infra`：祖先マーカーの検出、直下の一覧取得、パスと種類の確認。I/Oはバックグラウンドで行う。現在文書の`FileWatch`を、プロジェクト全体の再帰監視へそのまま拡張しない。
- `app`：ルート、検出理由、列挙要求と採否、展開・選択の論理状態を管理する候補。ツリーの要求IDは文書の読み込みIDとは分け、ルート世代＋ディレクトリ＋要求番号で逆順完了・A→B→Aを区別する。
- `ui`：ツリー描画、可視状態・幅、フォーカス、入力受付と本文レイアウト。マウス／キーのツリー操作で本文のNormal操作が同時発火しないようにする。
- 今回のツリー操作は`DocumentOperation::Open`へ接続しない。将来ファイルオープンを導入する場合は`Viewer::request_operation`経由の共通処理を使い、起点の識別と仕様変更を別途決定する。
- 別文書の読み込み成功時だけ履歴を確定し、戻った後の新規移動は進む側を破棄。同一文書の再読み込み、検索語保持、監視切り替え、Mermaidの古い結果除外は共通経路に委ねる。
- 共通選択パネルは一時的な絞り込みUI。常設可能な階層ツリーとは生存期間・入力が異なるため、同じコンポーネントにする前提を置かない。GPUIのツリーAPIの採用可否は実装前に別途調査する。

列挙はフォルダーを開いた分だけ行い、巨大な単一ディレクトリにも件数・時間・表示の上限を設ける案とします。上限到達を空フォルダーと区別して表示し、続きの取得／再試行を設計します。具体的な上限と仮想化の要否は計測後に決めます。非表示化やルート変更時は不要な要求を失効させ、キャンセルできないI/Oの完了も採用しません。
